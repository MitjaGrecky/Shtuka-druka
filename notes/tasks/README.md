# Задачи, передача, совместная работа (ред. 18.11.2026)

Активная очередь: [`../handoff.md`](../handoff.md) (одна строка на простую задачу). Сложная задача получает карточку `notes/tasks/<ID>.md` по шаблону ([../templates.md](../templates.md)); завершённые карточки остаются здесь, в очереди только ссылка. Сейчас карточек нет (заводить по мере появления).

## Состояния и владение
У каждой задачи один ответственный; главный инженер ведёт очередь и интеграцию, дизайнер владеет назначенным дизайнерским результатом, аудитор независимым заключением. Состояния: запланирована; в работе; ожидает входов (названы данные и владелец); на проверке; готова (доказательства записаны); отложена/отменена. Запись «поручить X» не равна выполнению: фиксировать факт передачи, доступность входов, ответ.
Перед работой: репозиторий, ветка, коммит, незакоммиченное. Область записи исполнителя узнавать коротким запросом, не чтением чужой истории. Общий файл на время правки имеет редактора (организационно, не блокировка): остальные шлют содержательные правки ему; проверять изменения перед сохранением. Синхронизация: `git pull --rebase --autostash`, чужое не сбрасывать. Перед коммитом смотреть diff, включать только свой результат; пуши пакетами.
Межплатный интерфейс: стороны, контакты, уровни, токи, протокол, ответные части, ориентация, версия; при изменении проверять обе платы, жгут, механику, ПО. Принятый пользовательский компромисс скрыто не менять.

## Передача
Сообщение: ID → что получено → где файл/коммит → проверки → ограничения → действие получателя. Локальный путь Windows не доступен облачному чату: передавать разрешённым каналом или через репозиторий с указанием версии. Получатель подтверждает вход и следующий шаг; нет канала: статус «готово к передаче» и ясная инструкция пользователю.
**Остановка:** карточка продолжения (цель, версия, изменённые файлы, проверки, незавершённый шаг, процессы, что нельзя перезапускать, следующее действие). Новая сессия сверяет изменения после записи и продолжает с незавершённого шага.

## Споры
1) одно утверждение, требование, объект с версией; 2) у каждой стороны основание, последствия, различающая проверка; 3) новые данные обновляют вывод, после двух циклов без них стоп: назначить расчёт, источник или эксперимент; 4) инженерный выбор в делегировании за главным инженером с обоснованием, аудитор отдельно оценивает достаточность доказательств, необоснованную находку можно закрыть с причиной; 5) существенный нерешённый спор о требованиях, допустимости риска, границах полномочий пользователю: обе позиции, последствия, рекомендация, один вопрос. Срок обсуждения дефект не закрывает; блокируется только зависимый шаг.

## Пробный пример (проверка процедуры)
Находка аудита A-… о конденсаторах связи A1: аудитор → инженеру одна находка; инженер выбрал WCAP-ASNP (P108, «принял главный инженер, R186»), аудитор подтвердил выбор; запись в `docs/ru/decisions/`, A1 rev 0.6; закрытие по доказательствам аудитора. Все шаги видны в журнале и `audit/`.
